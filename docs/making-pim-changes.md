# How to add or change things in Bluestone PIM

This guide is a cookbook. Each recipe shows the code to put in a migration's `up()` method to add or amend one kind of thing in Bluestone PIM. For a complete index of all API operations grouped by function, start with the [API changes guide](api-guide/index.md). Every code sample here passes the request and response schemas of the pinned API revision (checked offline). None of them has been run against a live tenant, so try new migrations on a test tenant first.

If you have not written a migration before, read [Initial PIM setup](initial-pim-setup.md) first. It covers configuration, creating the migration file and running it.

**Jump to:** [the three rules](#the-three-rules) · [ways to make a change](#ways-to-make-a-change) · [attributes](#attributes) · [categories](#categories) · [products](#products) · [variants](#variants) · [worked example](#worked-example-a-new-mandatory-attribute-inherited-by-variants) · [anything else](#any-other-change) · [troubleshooting](#troubleshooting)

## The three rules

1. **Every write gets a stable name.** The first argument after `$context` (for example `'warranty-definition'`) is how the SDK remembers that the write happened. If the migration is retried, completed writes are skipped and their saved result (usually an ID) is returned. Never change a name or its request once the migration has run anywhere.
2. **Use business numbers in code, IDs from the tenant.** Numbers such as `EXAMPLE-ATTRIBUTE-WARRANTY` are chosen by you and are the same in every tenant. IDs (such as `664cc80da825236207fe01a7`) are generated by Bluestone and differ per tenant. Use the ID returned by an earlier step, or look it up; do not copy IDs between tenants.
3. **Order matters.** Create things before you use them: categories → attribute definitions (and their select values) → products → variants and attribute settings.

## Ways to make a change

| Use | When | Example |
| --- | --- | --- |
| A ready-made runner method | A runner exists for the change | `$this->definitions->create(...)` |
| `$context->mutation()` + `executeTyped()` | Any other single write | Adding a select value |
| `PimJobRunner::submitAndWait()` | Writes that Bluestone finishes in the background (returns HTTP 202 or a task ID) | Bulk variant settings |

Inject what you need into the migration constructor; Symfony autowires it:

```php
use Youwe\BluestonePim\Api\Connector\PimConnector;
use Youwe\BluestonePim\Service\AttributeDefinitionMutationRunner;
use Youwe\BluestonePim\Service\CatalogRunner;
use Youwe\BluestonePim\Service\PimJobRunner;
use Youwe\BluestonePim\Service\ProductMutationRunner;

public function __construct(
    private readonly PimConnector $pim,
    private readonly AttributeDefinitionMutationRunner $definitions,
    private readonly ProductMutationRunner $products,
    private readonly CatalogRunner $catalogs,
    private readonly PimJobRunner $jobs,
) {
}
```

### The pattern for any write

Every recipe that does not have a ready-made runner follows the same shape:

```php
$result = $context->mutation(
    'stable-name',              // 1. never change once run
    'pim',                      // 2. API component
    'operationId',              // 3. from `bluestone:api:list pim`
    ['what' => 'is sent'],      // 4. everything that identifies this write
    function () { /* ... */ },  // 5. sends the request and returns a small result such as an ID
);
```

The fourth argument is fingerprinted. Reusing a name with different input stops the migration instead of silently doing something else. Return only small JSON values (IDs, numbers); they are saved in the tracking database.

`executeTyped()` checks the request against the API schema **before** sending it, so mistakes such as a misspelled field fail locally. A failure before anything is sent leaves the write safe to retry. Use `PimConnector::createdResourceId($response, 'a ...')` to read the ID Bluestone returns for something it created.

## Attributes

### Create an attribute definition

```php
$definitionId = $this->definitions->create($context, 'warranty-definition', 'EXAMPLE-ATTRIBUTE-WARRANTY', [
    'number' => 'EXAMPLE-ATTRIBUTE-WARRANTY',
    'name' => 'Warranty',
    'dataType' => 'text',
]);
```

- The third argument must equal `number`; it must be unique in the tenant.
- `dataType` is one of `boolean`, `integer`, `decimal`, `date`, `time`, `date_time`, `location`, `single_select`, `multi_select`, `text`, `formatted_text`, `pattern` or `multiline`.
- Optional fields: `description`, `groupId` (attribute group), `unit`, `contextAware` (different value per language), `internal`, `externalSource` and `restrictions`.
- Column, matrix, dictionary and compound attributes use their own operations (`createColumnDefinition`, `createMatrixDefinition`, `createDictionaryDefinition`, `createCompoundDefinition`) with [the pattern for any write](#the-pattern-for-any-write).

### Add options to a select attribute

Create the definition with `'dataType' => 'single_select'` (or `multi_select`), then add each option:

```php
$redId = $context->mutation('colour-option-red', 'pim', 'createSelectValue',
    ['definitionId' => $definitionId, 'value' => 'Red', 'number' => 'RED'],
    function () use ($definitionId): string {
        $response = $this->pim->executeTyped('createSelectValue', ['id' => $definitionId], [
            'headers' => ['context' => 'en'],
            'json' => ['value' => 'Red', 'number' => 'RED'],
        ]);

        return PimConnector::createdResourceId($response, 'a select value');
    });
```

Use `updateSelectValue` to rename an option and `reorderSelectValue` to change its position.

### Rename an attribute or change its description

```php
$changes = ['name' => ['value' => 'Warranty period'], 'description' => ['value' => 'How long the warranty lasts.']];
$context->mutation('rename-warranty', 'pim', 'updateMetadata', ['definitionId' => $definitionId, 'json' => $changes],
    function () use ($definitionId, $changes): string {
        $this->pim->executeTyped('updateMetadata', ['id' => $definitionId], [
            'headers' => ['context' => 'en'],
            'json' => $changes,
        ]);

        return $definitionId;
    });
```

Only the fields you send are changed. To change the data type, unit or restrictions, use `updateAttributeDefinition` (for simple attributes) with the full definition, the same fields as when creating it.

### Group attributes

```php
$group = ['name' => 'Logistics', 'number' => 'EXAMPLE-GROUP-LOGISTICS'];
$groupId = $context->mutation('logistics-group', 'pim', 'createAttributeGroup', $group, function () use ($group): string {
    $response = $this->pim->executeTyped('createAttributeGroup', [], ['headers' => ['context' => 'en'], 'json' => $group]);

    return PimConnector::createdResourceId($response, 'an attribute group');
});
```

Pass `'groupId' => $groupId` when creating a definition to put it in the group.

## Categories

### Create a catalog or category

Extend `AbstractPimMigration` instead of implementing `MigrationInterface`. It already holds the connector as `$this->pim`, so take `PimConnector $pim` in your constructor (without `private readonly`) and call `parent::__construct($pim)`. Then:

```php
$catalogId = $this->createCategory($context, 'shoes-catalog', ['name' => 'Shoes', 'number' => 'EXAMPLE-CATALOG-SHOES']);
$categoryId = $this->createCategory($context, 'boots-category', [
    'name' => 'Boots',
    'number' => 'EXAMPLE-CATEGORY-BOOTS',
    'parentId' => $catalogId, // omit for a top-level catalog
]);
```

### Rename a category

```php
$this->catalogs->updateDetailsOnce($context, 'rename-boots', $categoryId, ['name' => ['value' => 'Boots & wellies']], 'en');
```

### Give every product in a category an attribute (and make it mandatory)

A *Category Level Attribute* (CLA) puts an attribute on every product in a category. Bluestone applies it in the background, so each call is submitted and then polled:

```php
// 1. Add the attribute, with a value, to the products in the category.
$this->jobs->submitAndWait($context, 'warranty-on-boots', function () use ($categoryId, $definitionId): string {
    $response = $this->pim->executeTyped('createCatalogNodeAttribute', [
        'id' => $categoryId,
        'attributeDefinitionId' => $definitionId,
    ], ['headers' => ['context' => 'en'], 'json' => ['value' => '2 years']]);

    return PimConnector::createdResourceId($response, 'a task');
});

// 2. Also apply it to sub-categories (copyAttribute) and require a value on every product (mandatory).
$this->jobs->submitAndWait($context, 'warranty-on-boots-rules', function () use ($categoryId, $definitionId): string {
    $response = $this->pim->executeTyped('updateNodeAttributeValue', [
        'id' => $categoryId,
        'attributeDefinitionId' => $definitionId,
    ], ['json' => ['copyAttribute' => true, 'mandatory' => true]]);

    return PimConnector::createdResourceId($response, 'a task');
});
```

| Flag | Effect |
| --- | --- |
| `copyAttribute` | The attribute and its value also flow down to sub-categories and their products. |
| `mandatory` | Products in the category must have a value to be valid for synchronization. |
| `locked` | Products must keep the category's value. |

Existing product values are kept by default; add `'query' => ['forceCla' => true]` to overwrite them. A newly created CLA does not propagate to sub-categories until `copyAttribute` is switched on.

## Products

### Create a product

```php
$productId = $this->products->create($context, 'create-walking-boot', 'EXAMPLE-PRODUCT-BOOT', [
    'number' => 'EXAMPLE-PRODUCT-BOOT',
    'name' => 'Walking boot',
    'type' => 'SINGLE',
    'categories' => [$categoryId],
    'attributes' => [['definitionId' => $definitionId, 'values' => ['2 years']]],
]);
```

`type` is `SINGLE` (a normal product), `GROUP` (a variant group, see [variants](#variants)), `BUNDLE` or `FAMILY` (a group of variant groups).

### Change a product's name, number or description

```php
$this->products->update($context, 'rename-walking-boot', $productId, ['name' => ['value' => 'Hiking boot']]);
```

### Add an attribute value to a product

```php
$request = ['definitionId' => $definitionId, 'values' => ['2 years']];
$context->mutation('boot-warranty', 'pim', 'addProductAttribute', ['productId' => $productId, 'json' => $request],
    function () use ($productId, $request): string {
        $this->pim->executeTyped('addProductAttribute', ['id' => $productId], ['headers' => ['context' => 'en'], 'json' => $request]);

        return $productId;
    });
```

Values are always a list of strings, for example `['true']` for a boolean or `['1.5']` for a decimal. For a select attribute, pass the select value IDs.

### Change an attribute value on a product

```php
$values = ['values' => ['3 years']];
$context->mutation('boot-warranty-3-years', 'pim', 'updateProductAttribute',
    ['productId' => $productId, 'definitionId' => $definitionId, 'json' => $values],
    function () use ($productId, $definitionId, $values): string {
        $this->pim->executeTyped('updateProductAttribute', ['id' => $productId, 'definitionId' => $definitionId], [
            'headers' => ['context' => 'en'],
            'json' => $values,
        ]);

        return $productId;
    });
```

To change the value on many products at once, see `updateAttributesByIds` and `upsertAttributesByIds` in `bluestone:api:list pim --tag="Products attributes"`.

### Put a product in more categories

```php
$request = ['categoryIds' => [$categoryId]];
$context->mutation('boot-in-boots-category', 'pim', 'addProductToCategories', ['productId' => $productId, 'json' => $request],
    function () use ($productId, $request): string {
        $this->pim->executeTyped('addProductToCategories', ['id' => $productId], ['json' => $request]);

        return $productId;
    });
```

Categories the product is already in are left alone. Use `removeProductFromCategory` to take it out of one.

## Variants

Bluestone's product families work like this:

```text
GROUP product (variant group, e.g. "Walking boot")
├── variant (a SINGLE product, e.g. "Walking boot, size 42")
└── variant (e.g. "Walking boot, size 43")
```

Attributes on the group can be set as *Variant Level Attributes* (VLA). A VLA is automatically copied to every variant and can be made mandatory or locked on them.

### Turn a product into a variant group and add variants

```php
$context->mutation('walking-boot-becomes-group', 'pim', 'setProductGroup', ['productId' => $groupId],
    function () use ($groupId): string {
        $this->pim->executeTyped('setProductGroup', ['id' => $groupId]);

        return $groupId;
    });

$context->mutation('walking-boot-size-42', 'pim', 'addProductVariant', ['groupId' => $groupId, 'variantId' => $size42Id],
    function () use ($groupId, $size42Id): string {
        $this->pim->executeTyped('addProductVariant', ['id' => $groupId, 'variantProductId' => $size42Id]);

        return $size42Id;
    });
```

`setProductGroup` only works on a `SINGLE` product. A variant must be a `SINGLE` product that is not already in another group. You can also create the group directly with `'type' => 'GROUP'` in `$this->products->create()`.

### Make an attribute inherited by, and mandatory on, all variants

First [add the attribute to the group product](#add-an-attribute-value-to-a-product), then change its variant settings:

```php
$settings = ['copy' => true, 'mandatory' => true];
$context->mutation('warranty-vla-settings', 'pim', 'updateProductVariantAttribute',
    ['productId' => $groupId, 'definitionId' => $definitionId, 'json' => $settings],
    function () use ($groupId, $definitionId, $settings): string {
        $this->pim->executeTyped('updateProductVariantAttribute', ['id' => $groupId, 'definitionId' => $definitionId], [
            'json' => $settings,
        ]);

        return $definitionId;
    });
```

| Setting | Effect on the variants |
| --- | --- |
| `copy` | The attribute is copied to every variant, including variants added later. **Required for all the others.** |
| `mandatory` | Every variant must have a value. |
| `locked` | Every variant must keep the group's value (and so is also mandatory). |
| `definingAttributes` | The attribute is what tells the variants apart, such as size or colour. |

Variants that already have a value keep it. Add `'query' => ['forceVla' => true]` to overwrite their values with the group's.

### Do the same for many variant groups at once

`updateProductVariantsAttributeVlaSettings` applies the same settings to up to 100 groups. Every listed product must be a `GROUP` that already has the attribute. It runs in the background:

```php
$request = ['attributeDefinitionId' => $definitionId, 'productIds' => $groupIds, 'copy' => true, 'mandatory' => true];
$this->jobs->submitAndWait($context, 'warranty-vla-all-groups', function () use ($request): string {
    $response = $this->pim->executeTyped('updateProductVariantsAttributeVlaSettings', [], ['json' => $request]);

    return PimConnector::createdResourceId($response, 'a task');
});
```

Settings you leave out are **removed**, so always send every flag you want to keep.

For `FAMILY` products (which contain variant groups) the equivalent operations are `updateProductGroupAttribute` and `updateProductGroupsAttributeVlaSettings`, with the same settings.

## Worked example: a new mandatory attribute inherited by variants

**Goal:** add a new *Warranty* attribute, set it on a variant group so every variant inherits it automatically, and require every variant to have a value.

The steps, in order:

1. Create the attribute definition.
2. Add it to the variant group product, with the value the variants should start with.
3. Make it a Variant Level Attribute with `copy` (inherited) and `mandatory` switched on.

```sh
php bin/console bluestone:migrations:make "Add mandatory warranty attribute to boot variants"
```

Then fill in the generated class:

```php
<?php

declare(strict_types=1);

namespace App\Migration; // keep the namespace and class name the command generated

use Youwe\BluestonePim\Api\Connector\PimConnector;
use Youwe\BluestonePim\Migration\MigrationContext;
use Youwe\BluestonePim\Migration\MigrationInterface;
use Youwe\BluestonePim\Service\AttributeDefinitionMutationRunner;

final class Version20261102110000 implements MigrationInterface
{
    // Replace with the ID of an existing GROUP product in the target tenant.
    private const VARIANT_GROUP_ID = 'replace-with-variant-group-id';

    public function __construct(
        private readonly PimConnector $pim,
        private readonly AttributeDefinitionMutationRunner $definitions,
    ) {
    }

    public function description(): string
    {
        return 'Add a mandatory Warranty attribute inherited by the variants of a variant group';
    }

    public function up(MigrationContext $context): void
    {
        // 1. Create the attribute definition.
        $definitionId = $this->definitions->create($context, 'warranty-definition', 'EXAMPLE-ATTRIBUTE-WARRANTY', [
            'number' => 'EXAMPLE-ATTRIBUTE-WARRANTY',
            'name' => 'Warranty',
            'dataType' => 'text',
        ]);

        // 2. Add it to the variant group, with the value the variants should start with.
        $addRequest = ['definitionId' => $definitionId, 'values' => ['2 years']];
        $context->mutation('warranty-on-variant-group', 'pim', 'addProductAttribute',
            ['productId' => self::VARIANT_GROUP_ID, 'json' => $addRequest],
            function () use ($addRequest): string {
                $this->pim->executeTyped('addProductAttribute', ['id' => self::VARIANT_GROUP_ID], [
                    'headers' => ['context' => 'en'],
                    'json' => $addRequest,
                ]);

                return self::VARIANT_GROUP_ID;
            });

        // 3. Make it a Variant Level Attribute: copied to every variant and mandatory on each one.
        $vlaSettings = ['copy' => true, 'mandatory' => true];
        $context->mutation('warranty-vla-settings', 'pim', 'updateProductVariantAttribute',
            ['productId' => self::VARIANT_GROUP_ID, 'definitionId' => $definitionId, 'json' => $vlaSettings],
            function () use ($definitionId, $vlaSettings): string {
                $this->pim->executeTyped('updateProductVariantAttribute', [
                    'id' => self::VARIANT_GROUP_ID,
                    'definitionId' => $definitionId,
                ], ['json' => $vlaSettings]);

                return $definitionId;
            });
    }
}
```

The same code is in [`examples/migrations/Version20261102110000_AddMandatoryVariantAttribute.php.example`](../examples/migrations/Version20261102110000_AddMandatoryVariantAttribute.php.example).

Then check and run it:

```sh
php bin/console bluestone:migrations:migrate --dry-run
php bin/console bluestone:migrations:migrate
```

**Variations:**

- *All products in a category rather than one variant group:* use a [Category Level Attribute](#give-every-product-in-a-category-an-attribute-and-make-it-mandatory) instead of steps 2–3.
- *Many variant groups:* do step 2 for each group, then replace step 3 with the [bulk version](#do-the-same-for-many-variant-groups-at-once).
- *Every variant must have the same value:* use `['copy' => true, 'locked' => true]`.
- *Different value per variant:* leave out `values` in step 2, then [set the value on each variant](#change-an-attribute-value-on-a-product). With `mandatory` on, variants without a value are flagged as incomplete.

## Any other change

Find the operation:

```sh
php bin/console bluestone:api:list pim                      # every PIM operation
php bin/console bluestone:api:list pim --tag="Product variants"   # one area
php bin/console bluestone:api:list                          # other components (media-bank, labels, ...)
```

Read the operation's request fields in `resources/bluestone/revisions/<revision>/openapi/<component>.json` or the [online API reference](https://docs.api.bluestonepim.com/llms.txt), then use [the pattern for any write](#the-pattern-for-any-write). For other components inject their connector (for example `LabelsConnector`) and pass its component key (`'labels'`) to `mutation()`.

Some changes have dedicated helpers:

- **Images and files:** `MediaUploadRunner::upload()`; see [API connectors](api-connectors.md).
- **Going through every product:** `ProductCursorRunner::traverse()`; see [API connectors](api-connectors.md).
- **Large input lists:** `BatchProcessor::process()`; see [API connectors](api-connectors.md).
- **Bulk Operations service jobs:** `BulkOperationsJobRunner::submitAndWait()`.

## Troubleshooting

A failed migration prints a chain of errors: the migration, then the write that failed, then the cause. Read the last one.

| Cause | Meaning | Fix |
| --- | --- | --- |
| `ApiContractException` naming a field | The request does not match the API schema. Nothing was sent. | Correct that field. |
| `HTTP 400` on variant settings | `mandatory`, `locked` or `definingAttributes` was sent without `copy => true`. | Include `'copy' => true`. |
| `HTTP 409` | Something with that number already exists. | Use a different number, or look up the existing item and use its ID. |
| `HTTP 404` | An ID does not exist in this tenant, or the product is the wrong type. | Check the ID and product type (`SINGLE`/`GROUP`). |
| `A persisted mutation name cannot be reused...` | A write's input was changed but its name was not. | Give the changed write a new name. |

For all of these, nothing was changed in Bluestone. To continue:

1. Make the fix in the migration.
2. Give the write you changed a **new** name (for example `warranty-vla-settings-v2`). The SDK remembers each name with its original input, so a changed request under the old name is refused. Leave the writes that already completed unchanged.
3. Run `bluestone:migrations:migrate --retry`.

When Bluestone answers a write with an HTTP error, the failure is reported as `MutationInDoubtException` with the HTTP error as its cause, and that write's name is blocked from automatic retry. This is deliberate: in general the SDK cannot tell whether a server error changed anything. The steps above are safe for `400`, `404` and `409` because Bluestone rejected the request.

For any other cause (timeouts, `5xx`, the process stopping), check in Bluestone whether the change was made before retrying. See [mutation recovery](mutation-recovery.md). You can only edit a migration that has not been applied yet; to change something an applied migration did, write a new migration.
